# 模型中转站（Model Relay）模块文档

> 版本：v0.1（设计稿） · 状态：草案
> 目标：Rust 实现的 LLM API 统一中转网关，模块化 + 前后端分离

---

## 1. 项目定位

**模型中转站**是一个统一的大模型 API 网关/中继服务：

- **一个入口对接多家模型供应商**：OpenAI、DeepSeek、Anthropic、Gemini、Ollama（本地）等
- **对外提供 OpenAI 兼容接口**：`/v1/chat/completions`、`/v1/models` 等，客户端零改造接入
- **核心能力**：渠道管理、令牌鉴权、负载均衡、故障转移、限流、计费、用量统计、请求日志
- **拼车（渠道共享）**：多个用户共享同一批上游渠道，每人独立令牌、独立额度、用量归因到个人——这是本项目的**第一等公民功能**
- **配套管理后台**：浏览器可视化配置渠道/令牌/用户，查看统计图表

### 技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 后端 | Rust + axum + tokio | 异步 HTTP，流式转发（SSE） |
| 存储 | rusqlite（bundled SQLite） | MVP 零依赖，可平滑换 Postgres |
| 前端 | TypeScript + esbuild + Tailwind | 管理后台，前后端完全分离 |
| 部署 | 单二进制 + 静态文件 | 与 DocPI 同思路：`cargo build --release` 一个可执行文件 |

```
                        ┌─────────────────────────────────────────────┐
                        │                relay-server (bin)            │
                        │                                             │
  ┌───────────┐         │   ┌──────────────┐     ┌────────────────┐   │
  │ 管理后台    │──HTTP──▶│   │  relay-api    │────▶│ relay-store     │   │
  │ (frontend) │  /api/* │   │  路由/鉴权     │     │ 数据持久化       │   │
  └───────────┘         │   └──────┬───────┘     └────────────────┘   │
                        │          │                 ▲                 │

  │ 客户端     │──HTTP──▶│   │ relay-gateway │────▶│ relay-billing │     │
  │ AI工具/脚本│  /v1/*  │   │ 请求管线       │     │ 计费/配额/统计 │     │
  └───────────┘         │   └──────┬───────┘     └──────────────┘      │
                        │          │                                    │
                        │   ┌──────▼───────────────┐   ┌─────────────┐  │
                        │   │ relay-provider        │──▶│ OpenAI      │  │
                        │   │ 供应商适配层（trait）  │   │ DeepSeek    │  │
                        │   │                      │   │ Anthropic   │  │
                        │   └──────────────────────┘   │ Gemini      │  │
                        │                              │ Ollama 等    │  │
                        └──────────────────────────────┴─────────────┘
                                  ┌──────────────────┐
                                  │   relay-core      │ 共享：类型/错误/配置
                                  └──────────────────┘
```

**分层原则**：上层依赖下层，下层不依赖上层；核心业务（gateway/provider/billing）不感知 HTTP 层；存储可替换。

## 3. 模块总览

| 模块 | 类型 | 职责 | 依赖 |
|------|------|------|------|
| `relay-core` | lib | 通用类型、统一错误、配置模型 | 无 |
| `relay-store` | lib | SQLite 持久化、DAO、表结构迁移 | core |
| `relay-provider` | lib | 供应商适配（`Provider` trait + 各实现） | core |
| `relay-gateway` | lib | 请求管线：鉴权→限流→路由→转发→重试→记录 | core, provider, store, billing |
| `relay-billing` | lib | 额度/计费/用量统计 | core, store |
| `relay-api` | lib | HTTP 路由层（管理 API + OpenAI 兼容转发 API） | gateway, billing, store |
| `relay-server` | bin | 入口：配置加载、启动、优雅关闭 | 全部 |
| `frontend` | 前端 | 管理后台（独立目录，esbuild 构建） | relay-api |

> 早期可先用「单 crate + 严格模块边界」（同 DocPI 的 lib.rs 模式）快速起步，边界稳定后再拆 workspace——模块文档定义的就是最终形态，拆分只是目录级操作。

## 4. 模块详细设计

### 4.1 relay-core（核心基础）

**职责**：全项目共享的类型与基础设施，不依赖任何业务模块。

```rust
// 统一错误
pub enum AppError {
    BadRequest(String),
    Unauthorized(String),
    Forbidden(String),
    NotFound(String),
    RateLimited(String),        // 429
    ProviderError { status: u16, message: String },  // 上游渠道错误
    Internal(String),
}

// 配置（环境变量 + 可选配置文件，同 DocPI 的 config.rs 模式）
pub struct Config {
    pub port: u16,              // 默认 8080
    pub data_dir: String,       // 默认 ./data
    pub admin_username: String, // 默认 admin
    pub admin_password: String, // 必须通过环境变量设置
    pub default_timeout_ms: u64,
    pub max_retries: u32,
    // ...
}

// 核心数据模型（DTO，与存储层解耦）
pub struct Channel { id, name, provider_type, base_url, api_key_ref, model_mapping, weight, enabled, ... }
pub struct Token   { id, user_id, name, token_hash, status, quota_limit, used_quota, expires_at, ... }
pub struct Usage   { token_id, channel_id, model, prompt_tokens, completion_tokens, cost, latency_ms, ... }
```

**设计要点**：
- 错误类型带 HTTP 语义（`into_response` 在 api 层实现）
- 模型定义与存储结构分离（DTO），避免 SQL 细节泄漏到业务层

### 4.2 relay-store（数据层）

**职责**：SQLite 持久化，向上提供 DAO。

```rust
pub trait Store: Send + Sync {
    // 渠道
    async fn list_channels(&self) -> Result<Vec<Channel>>;
    async fn get_channel(&self, id: i64) -> Result<Option<Channel>>;
    async fn upsert_channel(&self, c: &Channel) -> Result<i64>;
    async fn delete_channel(&self, id: i64) -> Result<()>;
    // 令牌
    async fn get_token_by_hash(&self, hash: &str) -> Result<Option<Token>>;
    async fn create_token(&self, t: &Token) -> Result<i64>;
    // 用量日志
    async fn insert_usage(&self, u: &Usage) -> Result<()>;
    async fn query_usage(&self, filter: &UsageFilter) -> Result<Vec<Usage>>;
    // ...
}

// SQLite 实现
pub struct SqliteStore { conn: Mutex<Connection> }
```

**设计要点**：
- `Store` 用 trait 抽象 → 测试时可用内存实现 / 将来换 Postgres 无痛
- 复用 DocPI 已验证的模式：WAL、`create_dir_all`、启动建表
- API Key 加密存储（`api_key_ref` 指向加密后的值，不落明文）
- token 只存哈希（`sha256`），与 DocPI 一致

### 4.3 relay-provider（供应商适配层）

**职责**：屏蔽各供应商协议差异，向上提供统一异步接口。

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    fn name(&self) -> &str;                                   // "openai" / "deepseek" / ...
    async fn chat(&self, req: &ChatRequest, stream: bool) -> Result<ChatResponse>;
    async fn list_models(&self) -> Result<Vec<String>>;
}

// 流式
pub trait StreamProvider: Provider {
    fn chat_stream(&self, req: &ChatRequest) -> Result<Stream<Item = Result<ChatChunk>>>;
}

// 工厂：按渠道 provider_type 构造
pub fn create_provider(cfg: &ChannelConfig) -> Result<Box<dyn Provider>>;
```

**内置实现**：
- `OpenAIProvider`（openai-compatible 基类，覆盖绝大多数服务商）
- `DeepSeekProvider`（复用 OpenAI 兼容，仅调 base_url）
- `AnthropicProvider`（消息格式转换）
- `GeminiProvider`（rest 格式转换）
- `OllamaProvider`（本地）
- 自定义 Provider 只需实现 trait + 注册工厂

**设计要点**：
- OpenAI 兼容协议做基类，其他供应商做**格式转换适配器**
- 模型映射：渠道级 `model_mapping`（`gpt-4o → deepseek-chat` 等）
- 流式统一转成 OpenAI SSE 格式对外

### 4.4 relay-gateway（请求管线核心）

**职责**：一次转发请求的完整生命周期编排。

```
鉴权 → 限流 → 渠道选择 → 转发 → 失败重试/故障转移 → 用量记录 → 响应
│      │       │          │         │                │
│      │       │          │         └─ 上游 5xx/超时 → 换下一个渠道
│      │       │          └─ Provider::chat / chat_stream
│      │       └─ 权重轮询（weight）、健康检查过滤
│      └─ 令牌配额 + 全局限流（滑动窗口）
└─ Token 校验（sha256 比对）
```

```rust
pub struct Gateway {
    store: Arc<dyn Store>,
    billing: Arc<Billing>,
    providers: Arc<ProviderRegistry>,
}

impl Gateway {
    pub async fn forward(&self, token: &str, req: ChatRequest) -> Result<Response>;
    pub async fn forward_stream(&self, token: &str, req: ChatRequest) -> Result<SseResponse>;
}
```

**设计要点**：
- 管线各步骤独立函数，便于单测
- 重试策略：最多 N 次、指数退避、只对可重试错误（429/5xx/超时/连接失败）重试
- 故障转移：当前渠道失败后从渠道池选下一个
- 超时：上游超时（默认 60s）+ 总超时双层控制

### 4.5 relay-billing（计费与配额）

**职责**：额度控制与用量统计。

```rust
pub struct Billing {
    store: Arc<dyn Store>,
    pricing: Arc<PricingTable>,   // 各模型单价（输入/输出 token）
}

impl Billing {
    // 转发前：检查令牌/用户剩余额度
    pub async fn check_quota(&self, token: &Token, model: &str) -> Result<()>;
    // 转发后：按用量扣减 + 落日志
    pub async fn record_usage(&self, token: &Token, channel: &Channel, usage: &Usage) -> Result<()>;
    // 统计
    pub async fn stats(&self, filter: &StatFilter) -> Result<StatSummary>;  // 按天/模型/渠道
}
```

**设计要点**：
- 两种额度模式：`quota_limit`（总量限额）+ `used_quota`（累计），按需扩展余额模式
- **拼车双配额**：用户级配额（管理员给乘客设上限）+ 令牌级配额（可再细分），扣减时先令牌后用户
- 计费单价表可配置（`settings` 表），按模型 × 输入/输出分别计价
- 用量记录先落库再扣减，避免丢日志；失败可补偿
- 防滥用：用户级限流（RPM）+ 渠道级并发上限（拼车池保护）

### 4.6 relay-api（HTTP 层）

**职责**：路由注册、请求/响应序列化、鉴权中间件。

```
/v1/*          转发 API（OpenAI 兼容）
  GET  /v1/models
  POST /v1/chat/completions        （含 stream=true 的 SSE）
  POST /v1/completions             （可选，后续）
  POST /v1/embeddings              （可选，后续）

/api/*         管理 API（管理员，session 鉴权，同 DocPI auth 模式）
  channels  CRUD / 测试连通
  tokens    CRUD
  users     CRUD / 授权
  usage     日志查询 / 统计图表数据
  settings  站点设置
  auth      login / me / captcha
```

**设计要点**：
- 转发 API 只做「反代 + 鉴权」薄层，业务全在 gateway
- 管理 API 复用 DocPI 已验证的：图形验证码、session、scrypt 密码哈希
- SSE 响应使用 axum `Sse` + 逐块透传上游事件

### 4.7 relay-server（入口）


## 5. 数据模型（SQLite）

```sql
-- 用户
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,          -- scrypt
  role TEXT NOT NULL DEFAULT 'admin',   -- admin / operator
  quota_limit INTEGER DEFAULT -1,       -- -1 = 不限
  used_quota INTEGER DEFAULT 0,
  created_at TEXT NOT NULL
);

-- 渠道（供应商配置）
CREATE TABLE channels (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,                    -- 显示名
  provider_type TEXT NOT NULL,           -- openai/deepseek/anthropic/gemini/ollama
  base_url TEXT NOT NULL,
  api_key_enc TEXT NOT NULL,             -- 加密存储，绝不明文
  model_mapping TEXT DEFAULT '{}',       -- JSON：gpt-4o -> deepseek-chat
  weight INTEGER DEFAULT 1,              -- 负载均衡权重
  enabled INTEGER DEFAULT 1,
  status TEXT DEFAULT 'untested',        -- untested/healthy/unhealthy
  max_retries INTEGER DEFAULT 1,
  timeout_ms INTEGER DEFAULT 60000,
  created_at TEXT NOT NULL
);

-- 令牌（客户端调用凭证，只存哈希）
CREATE TABLE tokens (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  token_hash TEXT UNIQUE NOT NULL,       -- sha256
  status TEXT DEFAULT 'active',          -- active / disabled
  quota_limit INTEGER DEFAULT -1,
  used_quota INTEGER DEFAULT 0,
  expires_at TEXT,
  created_at TEXT NOT NULL
);

-- 用量日志
CREATE TABLE usage_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  token_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  channel_id INTEGER NOT NULL,
  model TEXT NOT NULL,
  prompt_tokens INTEGER DEFAULT 0,
  completion_tokens INTEGER DEFAULT 0,
  cost REAL DEFAULT 0,                   -- 按单价表折算
  latency_ms INTEGER DEFAULT 0,
  status TEXT NOT NULL,                  -- success / error / retried
  error TEXT,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_usage_created ON usage_logs(created_at);
CREATE INDEX idx_usage_token ON usage_logs(token_id, created_at);

-- 设置（KV）
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

> **拼车模型说明**：`channels` 表**没有归属字段**——渠道是全局共享的「拼车池」，所有启用渠道对全体用户开放（后续可加渠道授权组，按组分配渠道）。每位乘客的边界由 `users.quota_limit`（用户配额）+ `tokens.quota_limit`（令牌配额）双层控制，用量通过 `usage_logs.user_id/token_id` 精确归因。

## 6. 关键数据流

### 6.1 非流式转发

```
客户端 ──POST /v1/chat/completions (Authorization: Bearer sk-xxx)──▶ relay-api
  → gateway.forward()
    1. 校验 token（sha256 → tokens 表）→ 无效 401
    2. billing.check_quota() → 超额 429
    3. 渠道选择：轮询 enabled 渠道（权重），排除 unhealthy
    4. provider.chat(req) → 上游
    5. 失败 → 重试/换渠道（最多 N 次）
    6. billing.record_usage(用量) + 落 usage_logs
  → 返回上游响应（200）
```

### 6.2 流式转发（SSE）

```
客户端 ──POST /v1/chat/completions (stream: true)──▶ relay-api
  → gateway.forward_stream()
    1-5 同上（渠道选择 + 连接）
    6. 上游 SSE 逐 chunk 透传（OpenAI 格式统一）
    7. 收到 usage chunk / [DONE] → billing.record_usage() → 继续透传
```

### 6.3 故障转移

```
渠道A 5xx/超时/连接失败
  → 记录错误 → 渠道A 标记降级（cooldown）
  → 渠道池选渠道B 重试
  → 全部失败 → 502 返回，错误写入 usage_logs(status=error)
```

## 10. 部署方案（doc.yxpil.com）

现状：`doc.yxpil.com` 已跑 DocPI（Linux 服务器，nginx 反代 4322）。

**中转站部署形态**：独立二进制 + 独立端口（如 `8322`），由 nginx 反代，两个方案二选一：

### 方案 A：子域名 `relay.yxpil.com`（推荐）

```
DNS:  relay.yxpil.com  A 记录 → 服务器 IP

nginx:
  server {
    server_name relay.yxpil.com;
    listen 443 ssl;
    # ssl 证书沿用现有站点配置
    location / {
      proxy_pass http://127.0.0.1:8322;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      # SSE 关键：关闭缓冲
      proxy_buffering off;
      proxy_read_timeout 300s;
    }
  }
```

客户端 base_url = `https://relay.yxpil.com/v1`，管理后台 = `https://relay.yxpil.com/`

### 方案 B：子路径 `/relay`（同域名，省钱）

```
nginx（在 doc.yxpil.com 的 server 块里加）:
  location /relay/ {
    proxy_pass http://127.0.0.1:8322/;      # 注意结尾斜杠，剥掉 /relay 前缀
    proxy_buffering off;
    proxy_read_timeout 300s;
  }
```

客户端 base_url = `https://doc.yxpil.com/relay/v1`，管理后台 = `https://doc.yxpil.com/relay/`

### 服务端安全

- relay 监听 `127.0.0.1:8322`，**不对外网**，只允许 nginx 访问
- 管理端 session + 验证码（复用 DocPI 方案）；`ADMIN_PASSWORD` 环境变量必设
- 二进制用 musl 静态编译（zig 交叉编译工具链现成），解压即用

## 11. 设计原则（对照 DocPI 经验）

1. **模块化**：crate 边界 = 业务边界，依赖单向；测试时每层可独立 mock
2. **前后端分离**：前端纯 JSON API 消费方，后端不渲染 HTML（除 index.html 静态托管）
3. **安全**：API Key 加密存储、令牌只存哈希、管理端 session + 验证码、scrypt 密码哈希
4. **可观测**：所有转发请求落 usage_logs，管理端可查
5. **单一二进制**：relay-server 一个可执行文件 + public/ 静态目录，部署零依赖（musl 静态编译）
